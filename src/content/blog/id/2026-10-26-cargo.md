## TL;DR

Mendefinisikan _shared crate dependency_ di root `Cargo.toml` pada bagian `[workspace.dependencies]`, lalu direferensikan dengan `workspace = true` ke _member crate_ untuk menghilangkan perbedaan versi dan proses compile yang redundan.

## Cara yang salah

```toml
# member-a/Cargo.toml
[dependencies]
serde = { version = "1.0.200", features = ["derive"] }

# member-b/Cargo.toml
[dependencies]
serde = { version = "1.0.195" }
```

Melakukan _hardcoding_ versi eksternal dependency di setiap crate _member workspace_ dapat menyebabkan masalah pada proses maintenance tanpa disadari, seiring berkembangnya proyek dan developer yang ada proyek teresbut dalam menangani crate-crate yang terpisah, seperti nomor versi yang akan sangat mungkin berantakan di berbagai manifes.

Ketika package yang didefinisikan versinya itu konflik atau mungkin kombinasi fitur yang berbeda, Cargo sering kali me-resolve dan meng-coompile beberapa salinan dari crate yang sama persis. Perilaku ini dapat memperlambat waktu build, memperbesar ukuran binary, dan memicu compile error yang membingungkan ketika tipe yang diekspor dari dua versi dependency yang sama tidak dapat disuguhkan ke antar-crate yang ada di dalam workspace.

## Cara yang benar

```toml
# Cargo.toml (workspace root)
[workspace.dependencies]
serde = { version = "1.0.200", features = ["derive"] }

# member-a/Cargo.toml
[dependencies]
serde = { workspace = true }

# member-b/Cargo.toml
[dependencies]
serde = { workspace = true }
```

Pola pewarisan workspace milik Cargo ini memperkenalkan sentralisasi dependensi registri yang ada di root `Cargo.toml`. Dengan mendefinisikan semua _shared crate_ eksternal berbarengan di bawah `[workspace.dependencies]`, crate turunannya cukup mereferensikan `workspace = true` tanpa mengulangi versi atau flag bawaan.

Arsitektur ini mengubah pengelolaan dependensi menjadi hanya di satu titik. Memperbarui library, mengganti path crate, atau menangani _security advisory_ cukup dilakukan melalui manifes tingkat atasnya. Semua _member crate_ secara otomatis akan menggunakan apa yang diperbarui, dan memastikan konsistensi flag fitur, menghilangkan duplikasi proses compile yang tidak disengaja, serta menjaga manifes proyek tetap ringkas dan mudah dibaca.

## Tanya Jawab

### Bisakah member crate mengaktifkan fitur tambahan pada dependensi yang diwarisi?
Bisa. Kita dapat menambahkan crate-flag fitur khusus dengan mendeklarasikannya seperti `serde = { workspace = true, features = ["alloc"] }` di dalam manifes member. Cargo akan menggabungkan fitur lokal ini secara mulus dengan konfigurasi _shared workspace_ yang telah dibuat.

### Bisakah manifes root workspace juga membagikan metadata paket umum?
Bisa. Kolom seperti `edition`, `license`, `authors`, dan `repository` dapat ditempatkan di bawah `[workspace.package]` pada manifes root. Member crate kemudian mewarisinya menggunakan `edition.workspace = true` dsb.

### Bagaimana jika sebuah crate memerlukan versi `mayor` yang tidak kompatibel dari _shared crate_?
Member crate dapat memilih keluar (opt out) dari workspace, cukup dengan menentukan kebutuhan `version`-nya sendiri secara langsung tanpa menggunakan atribut `workspace = true`.
