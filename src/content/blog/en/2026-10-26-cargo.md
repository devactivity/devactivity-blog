## TL;DR

Define shared crate dependencies in your root `Cargo.toml` under `[workspace.dependencies]`, then reference them with `workspace = true` in member crates to eliminate version divergence and redundant compilation.

## The wrong way

```toml
# member-a/Cargo.toml
[dependencies]
serde = { version = "1.0.200", features = ["derive"] }

# member-b/Cargo.toml
[dependencies]
serde = { version = "1.0.195" }
```

Hardcoding external dependency versions across individual workspace member crates causes subtle maintenance overhead. As projects scale and different developers touch separate crates, version numbers drift apart across manifests.

When packages define conflicting versions or disparate feature combinations, Cargo often resolves and compiles multiple copies of the exact same crate. This behavior inflates build times, increases final binary footprints, and leads to cryptic compiler errors where types exported by two versions of the same dependency cannot be passed between workspace crates.

## The right way

```toml
# Cargo.toml (workspace root)
[workspace.dependencies]
serde = { version = "1.0.200", features = ["derive"] }

# member-a/Cargo.toml
[dependencies]
serde = { workspace = true }

# member-b/Cargo.toml
[dependencies]
serde = { workspace = true }
```

Cargo's workspace inheritance pattern introduces a centralized dependency registry in your root `Cargo.toml`. By defining all shared external crates under `[workspace.dependencies]`, child crates simply reference `workspace = true` without repeating versions or default flags.

This architecture turns dependency management into a single-point edit. Upgrading a library, replacing a crate path, or mitigating security advisories happens exclusively in the top-level manifest. All member crates automatically consume the updated definitions, enforcing consistent feature flags, eliminating accidental duplicate compilation, and keeping project manifests concise and readable.

## Q&A

### Can a member crate enable extra features on an inherited dependency?
Yes. You can supply crate-specific feature flags by declaring `serde = { workspace = true, features = ["alloc"] }` within the member manifest. Cargo seamlessly merges these local features with the shared workspace configuration.

### Can root workspace manifests also share common package metadata?
Yes. Fields such as `edition`, `license`, `authors`, and `repository` can live under `[workspace.package]` in the root manifest. Member crates then inherit them using `edition.workspace = true`.

### What if one crate requires an incompatible major version of a shared crate?
A member crate can opt out of workspace inheritance simply by specifying its own `version` requirement directly without using the `workspace = true` attribute.
